# Evidence Forge

청구항과 최대 7개 PDF를 입력받아, **구성요소 × 인용발명 전수 비교 매트릭스**를 만들고 발췌를 원문과 대조 검증한 뒤, 인용발명 조합·거절 이유 유형·구성대비 리포트를 **결정론적으로** 산출하는 React + FastAPI 애플리케이션입니다.

## 파이프라인

```
1. 청구항 분해        정규식으로 청구항 번호·(A)(B) 라벨·종속 관계 확정
                     중요도 · 하위 한정(core/qualifier) · 문헌 검색어를
                     LLM 1회로 함께 받음 (backend/app/claims.py)
2. 전수 비교          (청구항 × 문헌)마다 LLM 1회. 사실 판정만 받음 —
                     판정 라벨 · 직접성 · 원문 발췌 · chunk_id · 누락 제한
                     (backend/app/compare.py, 입력 해시로 캐시됨)
3. 발췌 검증          LLM 없이 문자열 대조. 원문에 없는 발췌는 직접 개시로
                     인정하지 않고 판정에 상한을 씌움 (backend/app/verify.py)
4. 커버리지 계산      판정 라벨 + 중요도 → 문헌별 단독 적합도 (coverage.py)
                     구성별 보완 필요 여부와 문헌 간 우열도 여기서 정의
5. 인용발명 선정      신규성 게이트 → 주 인용발명 자격 게이트 → 구성별 전 문헌
                     보완 분석 → 이득이 남는 동안 결합 → 종속항 체인 상속
                     (chain.py)
6. 보고서 조립        확정된 데이터에서 템플릿으로 문장 생성 (report.py)
```

4~6단계는 LLM을 부르지 않으므로 **같은 비교 매트릭스에서는 항상 같은 인용발명 조합과 보고서**가 나옵니다. 별도의 심사 판단 단계나 결합 동기·용이 도출 프롬프트는 실행하지 않습니다.

### 판정 정책

- **판정 라벨**: `동일` / `실질적 동일` / `일부 차이` / `일부 유사` / `차이` / `대응 없음` 6개만 사용합니다. `차이`·`대응 없음`은 대응으로 세지 않고 "추가 검색 필요"로 남깁니다.
- **정량 지표는 백분율이 아니라 셀 수 있는 값입니다**: 구성마다 `한정 n/m 개시 · 등급 · 근거 k곳`을 적고, 청구항마다 `구성 N개 — 완전개시 a · 부분개시 b · 미대응 c`를 집계합니다.
  - 종전에는 등급 밴드(95~99 · 90~94 …) 안의 위치를 백분율로 찍었습니다. 그 값은 두 가지가 문제였습니다. 첫째, 밴드 안에서 움직일 신호가 없었습니다 — 직접성·검증 상태는 대응으로 인정되기 위한 전제 조건(`has_correspondence`)이라 거의 항상 최고치이고, 하위 한정 개시율은 하나라도 빠지면 라벨 자체가 내려가 다른 밴드로 옮겨 가므로 밴드 안에서는 늘 1.0입니다. 실제로 한 보고서의 구성 20개 중 16개가 같은 값이었고, 숫자는 등급 이름을 되풀이할 뿐이었습니다. 둘째, `%`가 "청구항의 94%가 개시되었다"로 읽히는데 실제 뜻은 그것이 아니었습니다. **거짓 정밀도는 없느니만 못합니다.**
  - `n/m`은 분자·분모가 그대로 나가므로 독자가 바로 아래 근거 목록과 대조해 검증할 수 있고, 한정이 빠질 때마다 실제로 움직입니다. 대안 묶음은 하나로 셉니다. 한정 분해가 없는 구성(`m=0`)에는 아예 적지 않습니다 — 없는 분모를 지어내면 "0/0 개시"가 미개시로 오해됩니다.
  - `근거 k곳`은 개시 근거로 인용된 **서로 다른** 원문 위치 수입니다. 한 문단을 모든 한정의 근거로 되풀이 인용한 대응은, 그 문단 하나의 해석이 무너지면 구성 전체가 무너집니다.
  - 청구항 단위 집계를 따로 두는 이유: 결론(신규성·진보성·거절 곤란)을 실제로 정하는 것은 구성별 등급이 아니라 이 집계입니다. 적지 않으면 읽는 사람이 표를 되짚어 직접 셉니다.
- **선택적 한정**: `A, B 또는 C 중 적어도 하나`처럼 열거된 항목은 `alternative_group`으로 묶어, **하나만 개시되면 묶음 전체가 충족**된 것으로 봅니다. 개시되지 않은 나머지 대안은 차이점으로 적지 않고 커버율 분모에서도 뺍니다. 이 판단은 `models.missing_limitations()` 한 곳에만 두고 비교·검증 두 단계가 같이 씁니다 — 검증은 발췌 대조 결과로 `disclosed`를 뒤집으므로 누락 목록을 다시 계산해야 하는데, 각자 계산하면 비교 단계에서 걸러 낸 대안이 검증 단계에서 되살아납니다. 묶지 않으면 선택지를 넉넉히 나열한 청구항일수록 차이점이 길어져, 실제로는 청구항 문언을 읽어내는 문헌이 오히려 감점됩니다.
- **일괄 비교의 부분 구제**: 종속항은 여러 항과 여러 문헌을 한 프롬프트에 실어 1회로 비교합니다. 응답에서 **온전하게 돌아온 셀은 그대로 채택하고, 빠진 셀만** 단건으로 다시 받습니다. 한 응답에 셀 수십 개와 하위 제한 점검 수백 줄을 담아야 하므로 어딘가 빠지는 일은 드물지 않은데, 그때마다 전 셀을 다시 물으면 일괄 호출은 늘 헛돈이 되고 소요 시간은 셀 수에 그대로 비례합니다. 호출 자체가 실패하면 종전처럼 전 셀 단건 비교로 되돌려 판정을 반드시 받아 냅니다.
- **종속항 셀의 문맥 예산**: 종속항 행렬에는 부모항 구성이 아니라 "…에 있어서" 뒤의 추가 한정만 들어 있습니다. 한 줄짜리 한정을 판정하려고 문헌 전문을 실으면 같은 문헌을 종속항 수만큼 다시 읽히게 되므로, 종속항 셀은 `DEPENDENT_DOCUMENT_BUDGET_CHARS`(30,000자) 안에서 구성요소별 검색어가 적중한 청크와 그 앞뒤만 보냅니다.
- **동일·실질적 동일은 대상이 같아야 합니다**: 두 등급을 고르려면 그 구성이 무엇을 입력받아(입력) 무엇에 대해(대상) 무엇을 내놓는지(출력)를 문헌 원문에서 각각 지목할 수 있어야 합니다. 동작을 가리키는 낱말이 같아도(산출·판정·전송·예측) 그 동작이 걸리는 **대상**이 청구항과 다르면 용어 차이가 아니라 구성의 차이이므로 `일부 유사` 이하입니다. 종전 정의("용어만 다르며 기술적 의미와 작동 관계가 같음")로는 같은 기술분야에서 비슷한 목적을 가진 문장이면 대상이 달라도 `실질적 동일`로 올라갔습니다 — 실측 보고서에서 "광고 구간의 판매 가능성을 예측"하는 구성에 "웹사이트 방문자 속성으로 입찰을 예측"하는 문헌이 `실질적 동일` 94%로 붙었습니다.
- **core / qualifier**: 하위 한정은 그 구성이 무엇을 하는가(`core`)와 그 동작을 한정하는 조건·기준·파라미터(`qualifier`)로 나눕니다. core가 하나도 개시되지 않으면 대응으로 세지 않고, core는 개시되었는데 qualifier만 다르면 `일부 차이`입니다. 둘을 같은 무게로 세면 한정 문구가 섞인 조각이 함께 실패해, 대응 문단을 정확히 찾아 놓고도 구성 전체가 "대응 없음"으로 떨어집니다. 반대로 구성의 변별점 자체를 qualifier로 빼면 core가 공허해져 아무 문헌이나 대응하게 되므로, 분해 단계에서 두 방향을 모두 막습니다.
- **발췌 검증**: `…`로 축약된 각 구간이 모두 원문에 그대로 존재해야 `verified`입니다. 발췌는 진짜지만 모델이 존재하지 않거나 내용이 다른 `chunk_id`를 냈다면 문헌 전체에서 실제 청크 위치를 찾아 메타데이터만 복구합니다. 원문에 없는 문장을 인용한 경우에는 종전처럼 판정과 직접성을 낮춥니다.
- **청크 경계에 걸친 근거는 위치 문제이지 개시 문제가 아닙니다**: 공보 PDF는 단락과 무관한 자리에서 잘리므로 한 문장이 두 청크에 나뉘는 일이 흔합니다. 대표 발췌는 이미 "원문 대조를 통과했으면 위치를 특정하지 못해도 판정을 유지한다"고 정해 두었는데, 하위 한정 근거는 같은 상황에서 `disclosed`를 뒤집고 있었습니다. 그러면 문헌에 그대로 있는 한정이 '누락 한정'이 되고 구성 판정까지 강등되는데, 강등의 근거는 문헌의 내용이 아니라 청크를 어디서 잘랐는가입니다. 두 경로가 같은 규칙을 쓰도록 맞췄고, 위치는 그 문장이 **시작되는** 청크(가장 긴 앞부분이 들어 있는 청크)로 되돌립니다. 실측에서 검증 대상 하위 한정 근거의 7%가 이 경로로 버려지고 있었고, 그중 하나가 주 인용발명이 단독으로 개시한 구성을 미개시로 만들어 신규성 결론을 불필요한 문헌 결합으로 바꿨습니다.
- **신규성 우선**: 한 문헌이 모든 구성을 직접 근거·동일급 판정·누락 제한 없이 개시하면 단일 인용발명 신규성으로 확정하고, 문헌 결합 단계를 전부 건너뜁니다.
- **주 인용발명 자격 게이트**: 차별적 핵심 구성(중요도 4 이상)의 직접 개시량이 최고 문헌에 크게 못 미치면 후보에서 제외합니다. 다만 전체 점수가 낮아도 핵심 구성을 원문으로 직접 개시한 문헌은 평균에 희석되지 않도록 후보로 남깁니다.
- **보완 검토 대상 ≠ 미커버**: `동일`/`실질적 동일` + `direct` + 검증된 발췌 + 누락 한정 없음을 모두 만족해야 보완 검토를 끝냅니다. 주 인용발명이 `일부 차이`로 커버한 구성도 다른 문헌에 더 나은 대응이 있는지 반드시 확인합니다. **종속항도 같은 탐색을 돌립니다** — 종전에는 종속항만 대상을 공백(`uncovered`)으로 한정했는데, 그러면 상속한 문헌이 어떤 구성을 약하게라도 커버한 순간 그 구성은 탐색에서 빠지고, 같은 구성을 원문으로 직접 개시한 문헌이 있어도 영원히 채택되지 않습니다. 실측에서 "고유 식별값에 매칭된 영상을 호출하는 제어부"가 그런 기재가 전혀 없는 문헌의 "컴퓨팅 장치를 사용할 수 있다"는 총론 문단에 `일부 유사`로 붙었고, 그 구성을 실제로 개시한 문헌(`실질적 동일`·`direct`·검증됨)은 미채택으로 남았습니다.
- **부분 대응은 문장도 부분 대응으로 끝냅니다**: 판정이 `일부 차이`·`일부 유사`면 구성대비 문장은 "부분적으로 대응됩니다"로 끝납니다. 전부 "대응됩니다"로 끝내면, 모델이 판단 이유에 "…부분은 개시되어 있지 않다"고 적은 경우 "…개시되어 있지 않으므로 청구항의 '…' 구성과 대응됩니다"라는 자기모순 문장이 그대로 나갑니다. 같은 이유로 종합 요약의 유사점도 대표 구성이 부분 개시면 "부분적으로 공통"이라고 적고, 완전 개시된 구성이 하나라도 있으면 그쪽을 대표로 삼습니다 — 부분 개시 구성의 문언에는 개시되지 않은 한정까지 들어 있어서, 그대로 공통점으로 적으면 없는 개시를 단언하게 됩니다.
- **대응 없음 ≠ 차이 있음**: `uncovered`는 **대응 기재를 어느 문헌에서도 찾지 못한** 구성만 가리킵니다(`대응 없음`·`차이` 판정이거나 발췌 검증에 실패한 경우). 대응은 있는데 하위 한정이나 구현 방식이 다른 구성은 `residual`로 남겨 보고서의 차이점에 표시합니다. 이 둘을 유사도 임계값 하나로 뭉치면, 세부 구현이 다르다는 이유만으로 "어느 인용발명에도 대응 기재가 없다"는 보고서가 나옵니다.
- **공백을 메우는 문헌에는 유사도 하한을 걸지 않습니다**: 주 인용발명이 통째로 놓친 구성의 유일한 대응 기재를 가진 문헌은 판정이 `일부 차이`라도 결합 후보로 남깁니다. 결합 후 남는 차이는 버리지 않고 보고서의 차이점으로 남깁니다.
- **보조 인용발명**: 절대 성능이 아니라 **주 인용발명 대비 증분**으로 평가합니다. 점수 차가 아니라 판정 강도·직접성·발췌·검증 상태·누락 한정 중 하나 이상이 실제로 개선될 때만 보완으로 인정하며, 발췌가 없거나 검증에 실패한 대응은 판정 라벨이 높아도 채택하지 않고 탈락 사유를 남깁니다.
- **결합 한도**: 문헌 수에 상수 상한을 두지 않고, 보완 이득이 문턱(`MIN_SUPPLEMENT_GAIN`) 아래로 떨어지면 멈춥니다. 상한을 두면 세 번째 문헌이 어떤 구성의 **유일한** 검증 근거를 가지고 있어도 통째로 버려지고, 업로드된 문헌에 기재가 있는데도 그 구성이 "어느 인용발명에도 대응이 없다"로 보고됩니다. **종속항도 같은 규칙을 씁니다** — 부모항 조합을 상속한 뒤, 남은 공백에 검증된 대응을 새로 제공하는 문헌이 있는 한 계속 결합합니다. 종전에는 "공백을 **전부** 메우는 문헌 1건까지만"이었는데, 공백을 서로 다른 문헌 둘이 나누어 메우면 한쪽이 통째로 버려지고 그 문헌이 원문으로 개시한 구성까지 `uncovered`에 들어갔습니다. `uncovered`는 결합이 실패했다는 뜻이 아니라 어느 문헌에도 대응 기재가 없다는 **사실 진술**이라, 그렇게 적으면 이미 손에 든 문헌을 다시 찾아 나서게 됩니다. 다만 **공백을 메우지 않는 추가는 1건까지**입니다(`MAX_QUALITY_SUPPLEMENTS`). 공백을 메우는 추가에는 상한을 두지 않습니다 — 막으면 실제로 개시된 구성이 다시 미대응으로 보고되기 때문입니다. 반면 근거 품질만 올리는 추가는 커버리지를 바꾸지 않으면서 결합 문헌 수만 늘리는데, 종속항 하나에 인용발명 서너 건을 세운 거절 이유는 실무에서 그 자체로 설득력을 잃습니다. 예산이 떨어지면 대상을 공백으로 좁혀 계속 돕니다(루프를 끊으면 품질 개선 후보가 먼저 뽑혔다는 이유만으로 남은 공백이 방치됩니다).
- **구성 간 지시 관계 정합성**: 셀은 서로 독립적으로 판정되므로, 셀 하나만 보면 그럴듯해도 청구항 전체로 보면 성립할 수 없는 판정이 남습니다. 대표적인 것이 **선행 구성을 참조하는 구성**입니다 — 문헌에 "제1·제2 반사부재"가 없으면 "그 둘 **사이에** 배치되는 광원"도 그 문헌에 있을 수 없는데, 그 셀만 떼어 놓고 보면 "광원(패널 디스플레이)"이라는 문장이 있어 부분 대응이 나옵니다. 그렇게 남는 것은 "광원을 포함한다"뿐이고, 이는 그 분야의 어떤 장치나 만족하는 문장입니다. `consistency.py`가 청구항 문언의 "상기 X" 표현에서 지시 관계를 읽어(기술분야 사전 없이, 띄어쓰기 차이는 무시) **같은 문헌 안에서** 선행 구성을 넘지 못하도록 상한을 씌웁니다. 문헌 A가 앞 구성을, 문헌 B가 뒤 구성을 개시한 경우는 정상적인 결합이므로 건드리지 않습니다.
  - 상한의 하한선은 **부분 대응**(`일부 유사`)입니다. `차이`까지 내리면 그 구성은 미대응이 되고 그 문헌은 조합에서 빠져 근거 목록에서도 사라지는데, 지시 대상만 다를 뿐 구성의 나머지를 실제로 개시한 문헌이 그렇게 지워지면 심사관은 이미 확인된 문단을 다시 찾게 됩니다. 상한의 목적은 "완전 개시로 세지 않는 것"이지 "기재가 없다고 단정하는 것"이 아닙니다.
  - 상한이 걸린 구성은 하위 한정이 전부 개시(예: `한정 2/2`)인데 등급만 낮아 보입니다. 그 어긋남을 설명하는 문장을 차이점 줄에 반드시 적습니다.
- **미대응 구성의 인접 근거**: 대응으로 인정하지 않더라도 원문 대조를 통과한 가장 가까운 기재는 보고서에 함께 남깁니다. 감추면 심사관이 이미 확인된 문단을 처음부터 다시 찾게 되고, 어디까지 검토된 상태인지도 알 수 없게 됩니다. 어느 문헌을 남길지는 **강등되기 전** 판정으로 정하고 대표 발췌까지 후보에 넣습니다 — 보조 발췌만 훑으면 대표 발췌 하나로 그 구성을 가장 잘 개시한 문헌이 통째로 빠지고, 강등 후 값으로 재면 상한에 걸린 문헌들이 같은 등급으로 납작해져 인용발명 번호 순서가 승부를 가릅니다.
- **거절 곤란 판정**: 결합 후에도 핵심 구성이 미커버로 남으면 `rejection_impossible`로 표시합니다. 억지로 거절 이유를 만들지 않습니다.
- **결론을 보고서에 적습니다**: 청구항마다 어떤 거절 이유가 서는지(신규성 없음 · 진보성 검토 · 거절 이유 구성 곤란 · 구성대비 미완료)를 확정 사유와 함께 한 줄로 적습니다. 구성별 유사도만 늘어놓고 결론을 비워 두면 읽는 사람이 표를 되짚어 결론을 스스로 추정하게 되는데, 추정의 방향은 읽는 사람마다 다르고 그 추정이 보고서의 결론으로 인용됩니다.
- **등가 판단에 선 신규성은 그렇다고 밝힙니다**: 신규성 부정이 `실질적 동일`(용어가 다르나 기술적 의미가 같다는 **판단**)에 근거한 구성이 있으면 결론 줄에 그 구성을 나열합니다. 밝히지 않으면 보고서가 청구항 문언이 그대로 있었던 경우와 구별되지 않는 모습으로 나가고, 정작 다투어야 할 등가 여부가 검토 대상에서 빠집니다.
- **근거는 하위 한정 단위로 남깁니다**: 구성마다 대표 발췌 한 문장만 찍으면, 총론 한 줄로 구성 전체를 개시했다고 본 판정과 한정마다 실시 문장을 짚은 판정이 똑같은 문장으로 나갑니다. 등급이 같아도 그 판정을 다툴 수 있는지는 여기서 갈리므로, 개시로 인정한 하위 한정마다 그것을 뒷받침한 원문과 위치를 함께 적습니다.
- **근거 줄에는 출처 인용발명 번호를 반드시 붙입니다**: 구성 하나의 근거 목록에는 결합에 쓰인 **여러 문헌**의 발췌가 함께 들어갑니다. 번호를 적지 않으면 바로 위 구성대비 문장이 지목한 문헌 하나가 목록 전체의 출처인 것처럼 읽히는데, 실제로는 다른 인용발명의 문장이 섞여 있습니다. 그대로 인용하면 어느 문헌에 없는 기재를 그 문헌의 개시로 적게 되고, 그것이 곧 거절 이유의 근거로 나갑니다.
- **종합 분석 요약의 유사점은 한 줄 요약입니다**: 무엇이 공통인지(중요도가 가장 높은 대응 구성 하나)와 어디까지 공통인지(대응 범위·부분 개시 수)를 한 문장으로 적습니다. 종전에는 구성 원문 세 개를 " 및 "로 이어 붙였는데, 청구항 구성은 "…하는 단계 및", "…를 포함하되"처럼 다음 구성으로 이어지는 어미로 끝나는 일이 많아 문장이 연결어미 자리에서 깨졌고("…단계 및에 관한"), 무엇보다 그것은 요약이 아니라 이미 위에 구성별로 적힌 내용을 다시 나열한 목록이었습니다.

### 판정 캐시

LLM을 부르는 비교 판정(2단계)만 캐시합니다. 키는 `청구항 구성 원문 + 하위 한정·검색어 + 문헌 청크 + 판단 지침 + 프롬프트 버전 + provider/model`의 SHA-256입니다. 캐시는 히스토리 밖(`backend/data/comparison_cache/`)에 두어, 히스토리를 지워도 같은 입력이면 같은 판정이 재사용됩니다. `DELETE /api/cache`로 비웁니다.

키에 들어가는 하위 한정과 검색어는 분해 단계가 LLM에서 받는 값이라 실행마다 조금씩 달라집니다. 같은 청구항을 다시 분해하면 같은 뜻의 문장이 한두 글자 다르게 나오고, **그것만으로 이전 판정 캐시가 전부 미스**가 됩니다. 그래서 분해 결과를 `history/{job_id}/claim_elements.json`에 남기고 다음 실행이 그대로 재사용합니다. 취소 후 다시 눌러도 이미 받아 둔 셀 판정이 그대로 맞는 것은 이 저장 덕분입니다. 구성 원문까지 대조하므로 청구항 문언을 고치면 그 항만 다시 분해합니다.

### 동시 실행

(청구항 × 문헌) 셀은 서로를 참조하지 않고 소요 시간의 거의 전부가 CLI 응답 대기라, 초기 분석과 종속항 대비 모두 셀을 동시에 돌립니다. 동시 실행 수는 `FORGE_COMPARE_WORKERS`(기본 4)로 조절합니다. 호출 횟수도 프롬프트 내용도 달라지지 않으므로 토큰 비용은 그대로이고 대기 시간만 줄어듭니다 — 다만 동시 요청이 provider 한도에 걸려 실패하면 재시도가 붙으므로, 실패가 보이면 이 값을 낮춥니다.

판정은 완료 순서가 아니라 (청구항, 문헌) 순서로 다시 모읍니다. 완료 순서에 기대면 같은 입력에서도 실행마다 매트릭스가 달라집니다.

## 실행

```powershell
npm install
npm run dev
```

실행 전 포트 `5374`, `8330`을 점유한 기존 프로세스가 있으면 자동 종료하고 재시작합니다. Windows PowerShell에서는 `./run-dev.ps1`도 사용할 수 있습니다. 프론트엔드는 `http://localhost:5374`, 백엔드는 `http://localhost:8330/docs`에서 확인합니다.

### 개발 환경

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r backend/requirements.txt
uvicorn app.main:app --app-dir backend --reload
```

개별 실행이 필요하면 프론트엔드는 `npm --prefix frontend run dev`를 사용합니다. `docker compose up --build`로 함께 실행할 수도 있습니다.

## agy 연동

실제 CLI만 사용합니다. `LLM_PROVIDER=agy|claude|gpt`를 설정하면 각각 설치된 `agy`, `claude`, `codex` 실행 파일을 자동으로 사용합니다. agy와 Claude는 print 모드, OpenAI는 `codex exec` 형식으로 호출되며 CLI 인자는 `backend/app/agy.py`의 단일 어댑터에서 관리합니다. `shell=False`, 인자 배열, timeout, retry, stdout/stderr 분리를 사용합니다.

agy와 Claude의 `-p`는 값을 받는 플래그이므로 프롬프트는 항상 인자 배열의 마지막에 둡니다. Windows 명령줄은 32767자로 제한되므로 프롬프트가 24000자를 넘으면 임시 디렉터리의 파일로 저장해 `--add-dir`로 전달하고 CLI가 직접 읽게 합니다.

응답이 잘리거나 스키마가 어긋나면 그냥 다시 호출합니다. CLI 내부 저장소나 대화 로그를 뒤져 응답을 복구하지 않습니다 — CLI 내부 포맷에 의존하는 코드는 CLI가 바뀌는 순간 조용히 깨집니다.

## API

- `POST /api/jobs/prepare` → `POST /api/jobs/{id}/start` — 취소 가능한 작업 id를 먼저 받고 업로드와 분석을 시작합니다. `GET /api/jobs/{id}`로 진행 단계(`stage`)를, `DELETE /api/jobs/{id}`로 취소를 처리합니다.
- `GET /api/jobs/{id}/result`, `GET /api/jobs/{id}/download?format=md|txt`
- `GET /api/jobs/{id}/sources/{document_id}` — 분석 당시 히스토리에 보존한 원문 PDF
- `POST/DELETE /api/jobs/{id}/prior-art` — 결합 후 완전히 미커버된 구성과 일부 대응 뒤 남은 하위 한정을 웹에서 선행기술 검색하고, 진행 중인 검색을 취소합니다. 외부 호출이므로 분석 중 자동 실행하지 않고 이 요청에서만 동작합니다. 저장된 보고서가 있으면 실행할 수 있습니다 — 종속항 대비를 취소해 일부만 반영된 보고서도 대상입니다(취소는 확정된 항을 남깁니다).
  검색 결과는 코드가 다시 확인합니다: 제시된 URL을 열어 문헌번호가 그 페이지에 있는지 대조하고
  `verify`에 `verified`/`mismatch`/`unreachable`을 남깁니다. 구성대비 발췌를 원문과 대조하는 것과
  같은 이유이며, 확인하지 못한 결과도 지우지 않고 표시만 합니다(사내망이 외부를 막았을 수 있고,
  그때 지우면 검색이 조용히 0건이 됩니다). `FORGE_PRIOR_ART_VERIFY_TIMEOUT=0`이면 대조하지 않습니다.
  **웹 검색은 provider에 따라 동작이 다릅니다.** agy(`--sandbox`)는 터미널만 제한하므로 검색이
  되지만, claude는 `--tools ""`로 내장 도구를 전부 끄고 codex는 기본 샌드박스라 검색이 나가지
  않습니다. 이때 결과는 0건이 됩니다.
- `GET/DELETE /api/history`, `DELETE /api/history/{id}` — 저장된 결과·리포트를 조회하거나 지웁니다. 로그는 별도 보존됩니다.
- `DELETE /api/cache` — 판정 캐시 초기화.
- `POST /api/jobs/{job_id}/dependent-claims` — 기존 보고서에 청구항 1의 종속항을 복수로 추가. 본문은
  `{"claims":"【청구항 2】 ... 【청구항 3】 ..."}` 형식이며, 최초 분석에서 저장한 인용발명 추출
  캐시를 재사용해 PDF 업로드 없이 모든 신규 종속항을 한 번의 구성대비 호출로 처리합니다.
- `GET /api/logs`, `GET /api/logs/{job_id}`, `DELETE /api/logs` — 로그 목록·본문 조회, 전체 삭제
- `GET/PUT /api/settings`, `GET /api/settings/models`

분석마다 Forge 루트의 `history/{job_id}/`에 `result.json`·`report.md`·`report.txt`·`judgment.json`과
후속 종속항 분석용 `documents.json`이 남습니다. `judgment.json`은 문헌별 적합도 점수, 채택/미채택
역할, 구성요소별 판정과 근거를 담은 판정 추적 데이터입니다.
작업 로그는 Forge 루트의 `logs/`에 별도로 보존되며, 히스토리 삭제와 독립적으로 관리됩니다.
두 위치는 `FORGE_HISTORY_DIR`·`FORGE_LOG_DIR`로 옮길 수 있습니다. 컨테이너에서는 Forge 루트가
파일시스템 루트가 되므로 **반드시** 마운트된 볼륨 안을 가리켜야 합니다(`docker-compose.yml` 참고).

결과·문헌·청구항 원문의 원본은 이 히스토리이고, 서버 메모리의 작업 레코드는 캐시일 뿐입니다.
끝난 작업은 문헌 본문을 곧바로 놓아 주고(그래야 서버를 켜 둔 만큼 메모리가 늘지 않습니다),
버려진 작업 레코드는 `FORGE_JOB_RECORD_TTL_MINUTES`(기본 60분) 뒤에 정리됩니다. 정리된 뒤에도
같은 `job_id`로 결과 조회와 내려받기가 됩니다.

진행 중인 작업의 상태는 `backend/data/jobs/`에도 남습니다. 분석 도중 서버가 재시작되면
(포트 정리·크래시) 그 작업은 `interrupted`로 표시되어, 화면이 "작업을 찾을 수 없습니다" 대신
중단 사유를 보여 줍니다. 같은 입력으로 다시 실행하면 이미 끝난 판정은 판정 캐시에서
재사용되므로 남은 셀만 새로 대비합니다.

### 삭제

`DELETE /api/history/{id}`는 히스토리 폴더뿐 아니라 **레거시 사본(`backend/data/history/`)과
그 분석이 사용한 판정 캐시 항목**까지 함께 지웁니다. 레거시 사본을 남기면 기동 시 마이그레이션이
되살리고, 판정 캐시에는 업로드한 문헌의 **원문 발췌**가 들어 있어 그것을 남기면 지웠다고
생각한 문장이 디스크에 남습니다. 어느 캐시 항목이 그 분석의 것인지는 `cache_keys.json`에
기록해 둡니다. 로그도 마찬가지로 레거시 사본까지 지웁니다.

전체를 비우려면 설정 탭의 "판정 캐시 비우기"(`DELETE /api/cache`)를 함께 쓰십시오.

## 테스트

```powershell
pytest backend/tests
cd frontend
npm run build
```

`backend/tests/test_chain.py`가 선정 알고리즘의 회귀 테스트입니다 — 신규성 게이트, 증분 기반 보조 문헌 선정, 종속항 결합 한도, 동일 입력의 동일 출력을 고정합니다.

보안상 업로드는 PDF 확장자·파일 크기·개수·전체 크기를 검증하고, 파일명은 경로 요소를 제거해 저장합니다. 원문 PDF는 해당 분석의 `history/{job_id}/sources/` 안에만 보존되고 히스토리를 삭제할 때 함께 삭제됩니다. 기본 로그에는 PDF 원문·청구항 원문·CLI 원문 응답을 기록하지 않습니다.
